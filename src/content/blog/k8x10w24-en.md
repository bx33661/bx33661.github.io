# Security Issues in Object Storage Buckets

Reference article:

[Qi-Anxin Attack and Defense Community - A Brief Discussion of Security Issues in Applications Using S3-Standard Buckets](https://forum.butian.net/share/4340)

### **Private Read and Private Write**
In S3 bucket access control, private read and private write mean:

+ **Private read**: Only authorized users can read the bucket or its file contents.
+ **Private write**: Only authorized users can write data to the bucket or modify its contents.

By default, S3 buckets are private, and only users with access permissions can perform the relevant operations.

---

### Access Control Methods
To ensure private read and private write, S3 provides the following access control methods:

#### a. **Access Keys (AK/SK)**
```plain
{
  "AccessKeyId": "AKIAIOSFODNN7EXAMPLE",
  "SecretAccessKey": "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
}
```

+ **AK (Access Key ID)** and **SK (Secret Access Key)** are the core credentials for accessing S3.
+ Users with an AK/SK can interact with S3 directly through an API or SDK.
+ AK/SK must be managed carefully; a leak can lead to unauthorized access to a bucket.

#### b. **Pre-Signed URLs**
+ A pre-signed URL is a temporary authorization method for external users to access resources in a bucket.
+ A signed URL contains the resource path, validity period, and encrypted authorization information.
+ Users can access the specified resource through the signed URL without an AK/SK.
+ Suitable for temporary, short-term access, such as downloading or sharing files.

#### c. **Temporary Credentials (STS: Security Token Service)**
+ STS provides temporary credentials based on IAM (Identity and Access Management).
+ The credential validity period and permission scope can be limited.
+ Suitable for dynamically generated authorization, such as temporary access for multiple users.

### IAM/RAM Policies Explained
RAM (Resource Access Management) and

IAM (Identity and Access Management)

policies are core cloud-service access-control mechanisms used to precisely control what users, roles, and services can do with cloud resources.

---

### 1. **Basic Concepts**
#### **IAM vs. RAM**
+ **AWS IAM**: Amazon Web Services' identity and access management service.
+ **Alibaba Cloud RAM**: Alibaba Cloud's resource access management service.
+ **Core objective**: Both implement “who can perform what actions on which resources under what conditions.”

#### **Policy Components**
```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow/Deny",
      "Principal": "用户/角色/服务",
      "Action": "操作权限",
      "Resource": "资源ARN",
      "Condition": "条件限制"
    }
  ]
}
```

---

### 2. **Policy Types**
#### **a. Identity-Based Policy**
+ Attached to a user, user group, or role.
+ Defines the actions that identity can perform.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```

#### **b. Resource-Based Policy**
+ Attached directly to a resource (such as an S3 bucket policy).
+ Defines who can access that resource.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowUserAccess",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::
```

## Security Issues
### Hardcoding AK/SK Directly into the Front End
This leads to direct credential disclosure.

```javascript
// JS 
const ossClient = new OSS({
  accessKeyId: 'LTAI5tNvxxxxxxxxxx',     // 💀 完全暴露
  accessKeySecret: 'xxxxxxxxxxxxxxxxxxx', // 💀 完全暴露
  bucket: 'my-bucket',
  region: 'oss-cn-hangzhou'
});
```

It also creates another problem: the permissions granted are too broad.

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "oss:*",           // 💀 所有操作
      "Resource": "acs:oss:*:*:*"  // 💀 所有资源
    }
  ]
}
```
